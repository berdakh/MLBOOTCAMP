# Contributing

This guide describes how the book is built, so that every chapter, lab,
figure and solution has the same structure, runs in the same way and is
checked in the same way. Read it before editing a chapter, a lab, a check or
a solution.

## The structure of the repository

The book has three parts of chapters and a part of capstone projects. The
list of parts and the discovery of chapter folders are defined in one place,
`tools/book.py`, which every tool and test reads.

```
part1-foundations/            Chapters 1-18
part2-ml-at-scale/            Chapters 19-38
part3-deep-learning-systems/  Chapters 39-58
part4-capstones/              capN-slug/ (README.md brief, walkthrough.py -> walkthrough.ipynb), template/
appendices/                   glossary, equations, figures (generated), study and reference material
figures/                      every figure, as SVG, generated by tools/make_diagrams.py
src/                          churnlab (Part I), shoprank (Part II), scaleml (Part III), grading (exercise checks)
tests/  tools/                tests and build tools
```

## The chapter folder

Each chapter is a folder `chNN-slug` (two-digit number, lower-case slug with
hyphens) inside its part, containing five files:

| File | Contents | Edited by hand? |
|---|---|---|
| `README.md` | The chapter text | Yes |
| `notebook.py` | The lab source, in percent format | Yes |
| `notebook.ipynb` | The lab, generated from `notebook.py` by `tools/nbbuild.py` | **No** |
| `solutions.md` | Worked answers to every exercise and checkpoint question | Yes |
| `solutions.py` | Reference code for the graded exercises | Yes |

The automatic checks used by the lab are not in the chapter folder: they are
in `src/grading/chNN.py`, one module per chapter, and the lab imports them as

```python
from grading import chNN as grade
```

A folder is recognised as a chapter only when it contains `notebook.py`.

## The chapter text (`README.md`)

The chapter text is a self-contained explanation that can be read without
running anything. It has the following structure, in this order:

1. **Title**: `# Chapter N · Title`.
2. **Information line**, in italics: the part, the prerequisite chapters, the
   estimated reading and lab times, and the compute required, for example
   `*Part II · Prerequisites: Chapters 3, 4 and 5 · Estimated time: reading ~60 min, lab ~90 min · Compute: CPU*`.
3. **Links**: the Colab badge for the lab, a link to `notebook.ipynb` and a
   link to `solutions.md`.
4. **`## Learning objectives`**: a numbered list introduced by "After this
   chapter you should be able to:". Each objective begins with a verb that
   describes an observable ability (describe, derive, implement, measure,
   choose).
5. **Numbered sections**: `## N.1 Introduction`, `## N.2 …`, and so on, with
   subsections `### N.2.1 …` where needed. These carry the explanation, the
   figures and the equations. Each section should state what is being
   measured or built, why, and how to interpret the result.
6. **`## Key terms`**: the chapter's terms with short definitions. They are
   merged into the [glossary](appendices/glossary.md).
7. **`## Summary`**: the main points of the chapter, as a short list or a few
   paragraphs.
8. **`## Exercises`**: the lab's exercises, each described in one or two
   sentences (whether it is coded or written, and what it asks for), followed
   by a description of the checkpoint questions.
9. **`## Further reading`**: books, papers and documentation, each with the
   relevant chapter or section and, for papers, the venue and year.
10. **Next**: a final line `**Next:** [Chapter N+1 · Title](../chNN-slug/README.md)`.

`tests/test_teaching_content.py` checks that every chapter text has
`## Learning objectives`, `## Key terms`, `## Summary` and
`## Further reading`.

## The lab (`notebook.py` to `notebook.ipynb`)

### The build

```
partX-.../chNN-slug/notebook.py  ->  tools/nbbuild.py  ->  partX-.../chNN-slug/notebook.ipynb
```

* **Edit `notebook.py`, never the `.ipynb`.** Sources are percent-format
  Python: `# %%` starts a code cell, and `# %% [markdown]` starts a markdown
  cell whose every line is prefixed by `# `. Run `make notebooks` (or
  `python tools/nbbuild.py chNN` for one chapter) and commit both files. CI
  fails if they differ (`python tools/nbbuild.py --check`).
* Capstone walkthroughs are built in the same way, from
  `part4-capstones/capN-slug/walkthrough.py`.
* Committed notebooks have **no outputs** (`tools/check_notebooks.py`).
* `python tools/run_notebooks.py` executes labs in a fresh, empty artifact
  directory, which is the closest local approximation to a new Colab
  runtime. Every lab must pass it.

### The anatomy of a lab

A lab contains the following, in this order:

1. **Colab badge**: exactly
   `[![Open In Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/berdakh/MLBOOTCAMP/blob/main/partX-.../chNN-slug/notebook.ipynb)`,
   followed by one italic line on how to run the lab.
2. **Header**: `# Chapter N · Title`, then a bold line
   `**Part I · Chapter N · about MM minutes · CPU only**` (or the compute the
   lab needs), a short motivation, a numbered list introduced by "By the end
   you will be able to:", and **You will produce:** (the files or artifacts
   the lab leaves behind). `tools/make_toc.py` reads the lab time from this
   line.
3. **Read-first line**: a markdown cell
   `Read first: [Chapter N text](README.md) explains the concepts, equations and caveats behind this lab.`
4. **Setup cell**: copied verbatim from the template for the part,
   `tools/templates/partN_notebook.py`. It clones the repository in Colab,
   installs the part's requirements file, finds the repository root, chooses
   the artifact directory (the `USE_DRIVE` switch) and, in Part III, chooses
   the device and the compute budget.
5. **Catch-up cell**: rebuilds what this lab needs from earlier chapters (in
   Part I, by calling the `churnlab.bootstrap.ensure_*` functions) and imports
   the checks with `from grading import chNN as grade`. A lab never assumes
   that an earlier lab has run in the same session.
6. **`## Key terms`**: a table with the columns *Term*, *Plain meaning* and
   *Example here* (checked by `tests/test_teaching_content.py`).
7. **Numbered sections**: `## N.1 · Title`. Each consists of short prose,
   then code, then an **Expected:** line stating what the reader should see:
   ranges rather than exact floating-point values, unless the value is
   deterministic.
8. **Exercises**: usually two to four, placed in the sections where they
   belong (see below).
9. **`## Key equations`**: the chapter's main equations, each with one
   sentence in words. They are collected in the
   [equations appendix](appendices/equations.md).
10. **`## Troubleshooting`**: a table with the columns *Symptom*,
    *Likely cause* and *Fix*, for the failures a reader will actually meet in
    this lab.
11. **`## Checkpoint`**: four to six questions that a reader should be able
    to answer aloud, without notes. They are written in the style of interview
    questions.
12. **Next chapter**: a final line
    `**Next chapter:** [Chapter N+1 · Title](../chNN-slug/notebook.ipynb) — one sentence on why it follows.`
    Inside a part the link is to the sibling folder; across parts it is
    `../../partY-.../chNN-slug/notebook.ipynb`.

### Exercises, checks and solutions

An exercise is a markdown cell beginning `> **Exercise K.**` (K = 1, 2, …),
followed by a code cell with a stub and a call to its check:

```python
def leakage_free_split(df):
    # YOUR CODE HERE
    raise NotImplementedError


grade.ex1(leakage_free_split)
```

* Graded exercises are **always functions**: for SQL, a function that returns
  the query string; for a threshold, a function that returns it. Every check
  therefore has the same interface, `grade.exK(fn)`.
* Each `exK` in `src/grading/chNN.py` builds small tests and calls
  `churnlab.checks.run_check`, which prints `[PASS]`, `[FAIL]` (with a hint)
  or `[TODO]` and **never raises an exception**, so that the lab always runs
  from top to bottom with unfinished exercises. A check that needs an
  optional package declares it with `REQUIRES = {"torch"}`.
* Written exercises have no check: the cell says "Write your answer in the
  cell below", and a markdown cell follows.
* Every exercise has an answer in the chapter's `solutions.md` under a
  heading `## Exercise K · short title`, marked [verified] (verified by
  running), [expected] (expected; depends on a run) or [open-ended] (personal
  or open-ended). See [About the solutions](appendices/solutions.md).
* The reference code is in the chapter's `solutions.py`, as functions named
  `exK` with the same signature as the stub. `tests/test_solutions.py` runs
  every check against its reference solution, so a check that rejects its
  own solution fails CI; it also checks that every stub reports `[TODO]`.
* Every lab with a `## Checkpoint` has a `## Checkpoint answers` section in
  its `solutions.md`, answering each question.

The solutions are kept apart from the labs so that a reader can work without
seeing them, and in the same repository so that they stay consistent.

## Figures

* Figures are SVG files in `figures/`, drawn in Python with the small drawing
  kit `tools/svgkit.py` (the `Canvas` class) and registered with the
  `@diagram` decorator. The registering function returns
  `(filename, svg, caption)`.
* Figures are defined in one module per area (`tools/diagrams_l1.py`,
  `diagrams_l2a.py`, `diagrams_l2b.py`, `diagrams_l3a.py`, `diagrams_l3b.py`,
  `diagrams_cap_*.py` and `diagrams_docs.py`), so that authors working on
  different parts do not edit the same file. File names are prefixed by part
  (`l1-`, `l2-`, `l3-`), or `hb-` for background figures.
* `python tools/make_diagrams.py` (`make diagrams`) writes every SVG and the
  [list of figures](appendices/figures.md); `--check` fails if either is
  stale. Do not edit the SVG files or `appendices/figures.md` by hand.
* A figure should be simple: at most about eight boxes, one idea, short
  labels. `Canvas.box` raises `OverflowError` when text does not fit.
* Every figure must be used. In a chapter text, embed it with a relative
  path, `<img src="../../figures/NAME.svg" alt="…" width="100%">`; in a lab,
  with the raw GitHub URL, so that it also renders in Colab:
  `<img src="https://raw.githubusercontent.com/berdakh/MLBOOTCAMP/main/figures/NAME.svg" alt="…" width="100%">`.
  The `alt` text describes what the figure shows.

## Tables of contents

The tables of contents in the root `README.md` and in each part's `README.md`
are generated by `tools/make_toc.py` from the chapter folders, between the
markers `<!-- toc:start -->` and `<!-- toc:end -->`. Do not edit the text
between the markers. After adding, renaming or retitling a chapter, run
`python tools/make_toc.py`; `python tools/make_toc.py --check` fails if a
table is stale. A chapter's title is read from the `# Chapter N · Title` line
of its `notebook.py`.

## Style

* **Tone.** Write plain, precise, declarative English, as in a textbook. Do
  not use promotional language, business idiom or slang, emoji, or
  exclamation marks. Prefer the exact term to an approximate one, and define
  it at first use.
* **Never invent results.** Every claim about a model is a number from a
  recorded run, with its data split named. Do not state results, speed-ups or
  effects that were not measured; where a statement depends on hardware that
  was not used in the recorded runs (for example a T4 GPU), say so.
* **Mathematics.** Use `$...$` for inline mathematics and `$$` on its own
  line, before and after, for display mathematics. Unbalanced `$$` within a
  markdown cell is caught by `tests/test_teaching_content.py`. Follow each
  important equation with a sentence in words.
* **Nothing is opaque.** Build a thing by hand first (a split, a PSI, a retry
  loop), then show the library function that does it and name its source
  file.
* **CPU first in Parts I and II.** Core cells finish in seconds to a few
  minutes on a free Colab CPU. GPU material in these parts is in a clearly
  labelled optional section guarded by `RUN_GPU_EXTENSION = False`, and no
  later chapter depends on it. Part III is written for a T4 GPU and must also
  run, with the reduced budget, on a CPU.
* **Accurate about Colab.** What cannot run in Colab (Docker, a public server)
  is taught by generating files and explaining them; the text states plainly
  that running them is an optional extension outside Colab.
* **Links.** Link to other chapters with relative paths: to the chapter text
  (`../chNN-slug/README.md`) in prose, and to the lab
  (`../chNN-slug/notebook.ipynb`) when the reader is meant to run it.
* **Spelling.** British or American spelling, consistently within a file.
* **Cells.** Keep cells short. A reader should be able to predict what a
  cell prints.

## Checks

Run everything that CI checks before submitting a change:

```bash
make check                       # notebook sync, figures, notebook structure, links, tests
python tools/make_toc.py --check # tables of contents (also covered by the tests)
make lint                        # ruff on the packages, tests, tools and reference solutions
```

`make check` runs `tools/nbbuild.py --check`, `tools/make_diagrams.py --check`,
`tools/check_notebooks.py`, `tools/check_links.py` and `python -m pytest`. The
tests need no network. Checks that need PyTorch are skipped when it is not
installed.
